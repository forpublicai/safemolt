1. **BLOCKER — Registration-first locks can deadlock with the D4 completion path.** [evaluations/db.ts:380](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/db.ts:380), [evaluations/db.ts:480](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/db.ts:480), [evaluations/db.ts:621](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/db.ts:621)  
   `claimProctorSession` locks the registration before participant inserts take agent FK locks. `startEvaluationWithEffect` also updates the registration before its challenge or certification-job insert takes an agent FK lock. At the same time, D4 completion locks the agent first and then updates the registration. Each transaction can wait for the row held by the other transaction, which causes `40P01`. Crossed proctor claims can also lock two agent rows in different orders.  
   Minimal fix: lock all referenced agent rows first, in agent-id order, and then lock or update the registration. Keep session and job locks after those locks.

2. **MAJOR — Memory evaluation start can leave partial state and reopen a terminal registration.** [evaluations/memory.ts:434](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/memory.ts:434), [evaluations/memory.ts:438](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/memory.ts:438), [evaluations/memory.ts:450](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/memory.ts:450)  
   The PoAW branch inserts the challenge and changes the registration before `prepareEventBatch`. A duplicate idempotency key therefore throws after the mutation. The certification branch also creates a job before event preflight. Its `await` yields after the first registration check. A concurrent completion can make the registration terminal, after which this path sets it back to `in_progress`.  
   Minimal fix: build and preflight the full event batch before any write. Use a synchronous certification-job helper in the decisive section, or re-check the registration after the await and before all writes.

3. **MAJOR — Completion hides event-log uniqueness errors as normal refusals.** [evaluations/db.ts:654](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/db.ts:654)  
   `completeRegistrationAtomically` catches every `23505`. If `evaluation.completed` uses an idempotency key that already exists, `idx_events_idem` rejects the event and rolls back the complete transaction. The catch returns `false`, and the later read reports `not_actionable` instead of the event error. Memory mode throws during preflight, so the stores differ.  
   Minimal fix: handle only the two expected evaluation-result uniqueness constraints. Re-throw `idx_events_idem`, result primary-key collisions, and all other `23505` errors.

4. **MAJOR — Vetting start is not conditionally locked and does not return decisive flags.** [agents/db.ts:825](/Users/mohsin/Github/safemolt/src/lib/store/agents/db.ts:825), [agents/db.ts:836](/Users/mohsin/Github/safemolt/src/lib/store/agents/db.ts:836)  
   `eligible` reads an unvetted agent without a row lock. A concurrent vetting completion can vet the agent before the challenge insert gets its FK lock. The insert can then continue and create a challenge for an already-vetted agent. On a zero-row insert, a separate read can also report `agentExists: false` if deletion occurs after the decision.  
   Minimal fix: select and lock the target agent in the same statement. Gate the insert on the locked row’s `is_vetted` value. Return `agent_exists`, `created`, and `already_vetted` from one final scalar projection.

5. **MAJOR — Claim outcomes are reconstructed from later reads.** [agents/db.ts:348](/Users/mohsin/Github/safemolt/src/lib/store/agents/db.ts:348), [agents/db.ts:420](/Users/mohsin/Github/safemolt/src/lib/store/agents/db.ts:420), [agents/memory.ts:256](/Users/mohsin/Github/safemolt/src/lib/store/agents/memory.ts:256), [agents/memory.ts:326](/Users/mohsin/Github/safemolt/src/lib/store/agents/memory.ts:326)  
   Both outcome wrappers call the mutation and then inspect current state. For example, a claim can lose because the agent was already claimed, and a concurrent deletion can then make the wrapper report that the agent did not exist. In memory mode, deletion can occur while the inner call awaits event dispatch. This does not deliver the required classified claim flags.  
   Minimal fix: make each decisive claim operation return `agentExists`, `claimed`, and the claimed row directly. In PostgreSQL, project them from the locked target and claim CTEs. In memory, compute and return them in one synchronous section.

6. **MAJOR — Memory actor checks override valid refusal classifications.** [evaluations/memory.ts:287](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/memory.ts:287), [evaluations/memory.ts:368](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/memory.ts:368)  
   `addSessionMessage` checks the sender before it checks active-session and participant eligibility. `claimProctorSession` checks both agents before it checks terminal status, an existing session, or an existing result. A stale request after withdrawal can therefore receive a memory `23503`, while PostgreSQL inserts no row and returns `null`.  
   Minimal fix: classify all no-write conditions first. Check actors only after the operation is otherwise eligible, immediately before the mutation.
