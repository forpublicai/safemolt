1. **BLOCKER** — [src/lib/store/evaluations/db.ts:1357](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/db.ts:1357), [src/lib/store/evaluations/memory.ts:946](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/memory.ts:946)  
   `submitCertificationTranscript` is not fenced by the nonce that the request validated. A request can validate the old nonce just before expiry, pause, and then lose to a certification restart that refreshes the job in place. The old request then submits by job ID only. It sees the refreshed `pending` status and new future expiry, so both stores accept a transcript authorized by the expired nonce. This defeats nonce rotation and can attach an old attempt to the refreshed job.  
   Minimal fix: pass the validated nonce into `submitCertificationTranscript`. Add `nonce = expectedNonce` to the PostgreSQL CAS and the equivalent memory check.

2. **MAJOR** — [src/lib/store/evaluations/db.ts:546](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/db.ts:546)  
   The certification start operation does not lock the selected job in `live`. A concurrent transcript submission can change an expired `pending` job to `submitted` after `live` reads it but before `refreshed` updates it. Because `refreshed` tests the materialized `live.status`, it can overwrite the current job back to `pending` and rotate its nonce. The operation can also return an old job projection while the stored row has changed.  
   Minimal fix: make `live` a locking read, such as `... LIMIT 1 FOR UPDATE OF cj`, before the mutually exclusive arms use it. Keep the nonce fence from finding 1 because lock order alone does not reject an old submission that starts later.

3. **MAJOR** — [src/lib/store/evaluations/db.ts:108](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/db.ts:108)  
   Registration does not implement the required raced-`23505` classification. During a mixed-version race, or against another writer that does not take the new agent lock, both operations can observe no active registration. The losing insert raises `idx_eval_reg_active`; this function propagates a 500 instead of returning `existing`. Its transaction and event correctly roll back, but the outcome contract is not delivered.  
   Minimal fix: catch only `23505` for `idx_eval_reg_active`, then rerun the conditional classifier with a fresh snapshot so it returns `existing` or `already_passed`.

4. **MAJOR** — [src/lib/store/agents/db.ts:1014](/Users/mohsin/Github/safemolt/src/lib/store/agents/db.ts:1014), [src/lib/store/agents/memory.ts:942](/Users/mohsin/Github/safemolt/src/lib/store/agents/memory.ts:942)  
   Vetting refusal precedence differs between stores. PostgreSQL checks `agentRow.is_vetted` before challenge mismatch, consumption, and expiry. Memory checks those challenge states first. Therefore, a vetted agent replaying a consumed challenge gets `already_vetted` in PostgreSQL and `consumed` in memory; a foreign or expired challenge has the same divergence. This can also send a consumed replay through an idempotent “already vetted” response path.  
   Minimal fix: in the DB classifier, use `already_vetted` only when the challenge row is absent. For a present challenge, classify `mismatch`, `consumed`, and `expired` before any fallback. A valid unconsumed challenge will still reach `completed`.

5. **MINOR** — [src/lib/store/evaluations/memory.ts:431](/Users/mohsin/Github/safemolt/src/lib/store/evaluations/memory.ts:431)  
   Memory certification and PoAW starts validate prepared events only on branches that emit. PostgreSQL renders and validates the events before it executes the conditional SQL, including `refreshed`, `existing_job`, and `none` outcomes. Thus an invalid prepared event makes PostgreSQL refuse before any write, while memory can refresh a nonce or return a no-op outcome successfully.  
   Minimal fix: substitute and call `validatePreparedEvents` before the first state-based return. Call `prepareEventBatch` only when the registration CAS will emit.
